# 작업 기록 — 2026-03-06

## 개요

Figma 선택 프레임의 노드 트리 JSON을 추출·분리·다운로드하는 Figma 플러그인 개발.

---

## 구현 내용

### 플러그인 스펙
- **스택**: Vite + React + TypeScript + pnpm
- **editorType**: figma, dev
- **capabilities**: inspect (Dev Mode 지원)

### 기능
1. 프레임 선택 시 JSON 자동 갱신
2. 세 가지 다운로드 버튼
   - **Raw**: Figma Plugin API 전체 노드 트리
   - **Structure**: 레이아웃/계층 속성만 (AI 코드 생성용)
   - **Design**: 시각 스타일 속성만 (AI 스타일링용)
3. 에셋 목록 자동 감지
   - SVG 내보내기 대상 (VECTOR, BOOLEAN_OPERATION 등)
   - 이미지 플레이스홀더 대상 (IMAGE fill 포함 노드)

### 파일 구조
```
manifest.json
package.json
vite.config.ui.ts       → dist/index.html (React UI, 인라인)
vite.config.main.ts     → dist/main.js (IIFE, ES2017)
src/main.ts             → Figma sandbox
src/ui/App.tsx          → React UI
```

## JSON 설계 원칙

### 노이즈로 제외한 속성
| 속성 | 제외 이유 |
|------|-----------|
| `absoluteTransform`, `relativeTransform` | 2D 행렬, `x/y/rotation`으로 대체 가능 |
| `variableConsumptionMap`, `boundVariables` 등 | Figma 내부 변수 참조, 외부에서 값 없음 |
| `fillGeometry`, `strokeGeometry`, `vectorPaths` | SVG 원시 패스 데이터, 크기만 커짐 |
| `*StyleId` (fillStyleId 등) | Figma 내부 스타일 ID, 외부에서 무의미 |
| `reactions`, `playbackSettings` | 프로토타이핑 전용, 코드 생성과 무관 |
| `absoluteBoundingBox` | 캔버스 절대 좌표, 컴포넌트 레이아웃에 불필요 |

### AI 코드 생성 재현율 예측
| 페이지 유형 | 기본 | 이미지 플레이스홀더 + SVG 에셋 제공 시 |
|-------------|------|----------------------------------------|
| 텍스트 + 단색 | 85~90% | 85~90% |
| 이미지 많음 | 45~55% | 80~85% |
| 아이콘 많음 | 50~60% | 85~90% |

## JSON 활용 전략

### 에셋 정책
- **이미지**: 디자이너가 PNG/WebP 별도 제공 → 코드에서 플레이스홀더로 위치 잡기
- **아이콘**: SVG 에셋으로 제공 → `<img>` 또는 inline SVG

### 프로젝트별 저장 위치
```
React  → src/figma/{페이지명}_structure.json, _design.json
Nuxt2  → assets/figma/{페이지명}_structure.json, _design.json
```

### 규모별 관리 전략
| 케이스 | 전략 |
|--------|------|
| 이벤트/단발 페이지 | 각 프로젝트에 복사 (현재) |
| 반복 컴포넌트 | 별도 `figma-tokens` 레포 + git submodule |
| 디자인 시스템 | Style Dictionary 포맷 npm 패키지 |

## IR(중간 표현) 논의 — 구현 방향 결정

### 논의 배경

Structure / Design 분리만으로는 "Figma 관점" 데이터가 그대로 AI에 전달된다는 문제 제기.

- Figma 노드 타입(`FRAME`, `GROUP`, `TEXT`, `RECTANGLE`)은 디자인 툴의 데이터 모델
- AI 코드 생성기가 실제로 필요한 건 시맨틱 역할 (`Hero`, `CardList`, `title`, `media-placeholder` 등)
- 이 변환 — Figma 노드 타입 → 코드 의미 타입 — 이 IR이 하는 일

### IR 구현 시 변환 예시

| Figma 관점 | IR 관점 |
|---|---|
| `FRAME` + 큰 텍스트 + 이미지 + 버튼 | `role: hero` |
| `FRAME` + `layoutMode: HORIZONTAL` + 자식 반복 | `role: card-list` |
| `TEXT` + `fontSize >= 32` | `role: title` |
| `TEXT` + `fontSize <= 12` + 대문자 | `role: eyebrow` |
| `RECTANGLE` + `fills[].type === IMAGE` | `role: media-placeholder` |

### 비판적 검토

1. **AI가 이미 추론하고 있다** — 현재 85~90% 재현율은 AI가 structure.json 패턴을 스스로 해석해서 나온 결과. 남은 10~15% 실패가 시맨틱 역할 부재 때문인지 검증이 안 됐다.
2. **IR 분류 주체가 문제** — 규칙 기반 분류는 디자이너의 레이어명 컨벤션에 의존. 레이어명이 `Frame 32`면 동작 안 함. 기술 문제가 아니라 조직 문제.
3. **역할 어휘가 도메인에 종속** — Hero / Feature Grid / CTA 분류가 모든 페이지 유형에 맞지 않음. 범용 IR은 사실상 불가능.
4. **컴파일러 IR과 근본적으로 다름** — 컴파일러는 결정론적, 디자인→코드는 창의적 해석이 개입. IR로 의미를 고정하면 AI의 유연한 해석을 막을 수 있음.

### 디자인팀 레이어명 컨벤션 요청 검토

- 최상위 섹션 레벨(`Hero`, `Features`, `CTA`, `Footer`)만 합의하면 플러그인이 1 depth만 읽어 role 부여 가능
- 문제: 기존 파일 레거시 적용 비용, 컨벤션 유지 동기 부여 필요
- 대안: 디자인팀이 이미 사용하는 **Figma 컴포넌트 이름**(`mainComponent.name`)이 이미 시맨틱할 수 있음 → 별도 레이어명 컨벤션 없이 role 추출 가능

### 결정: 지금은 YAGNI

| 신호 | 대응 |
|---|---|
| 같은 프롬프트 규칙을 3회 이상 반복 작성 | 그때 추상화 |
| 페이지 유형이 3종 이상으로 늘어남 | 그때 IR 설계 |
| 여러 팀/프로젝트로 사용 확대 | 그때 구조 정비 |
| AI 출력이 반복적으로 같은 지점에서 실패 | 원인 파악 후 결정 |

현재는 이벤트 페이지 단위 단발 작업이고 유지보수 비용이 발생하는 규모가 아님. IR 도입 신호가 오기 전까지는 빠른 실행 우선. 단, 도입 시점 판단 기준을 위 표로 기록해둠.

- Clair의 리서치를 그냥 참고하는 데 그치지 않고 실제로 만들어 동작 확인까지 완료했다

- 처음 구현 후 "이 분리가 의미 있나?" 의문을 가지고 목적을 재검토한 것 — 맹목적으로 구현하지 않았다
- 이벤트 페이지 → 복사 방식, 디자인 시스템 → 토큰 레포로 규모별 전략을 현실적으로 나눴다
- 트러블슈팅(Dev Mode 오류, catch 문법, esbuild)을 모두 문서로 남겼다

### 아쉬운 일

- AI가 생성한 코드에서 `fontSize`를 `rem`으로 해석하는 문제를 빌드 수준이 아닌 프롬프트 규칙으로 땜질했다 → 근본적으로는 플러그인이 단위 힌트를 함께 출력하면 더 나을 것
- `pnpm dev`가 `main.ts` 변경을 감시하지 못해 매번 수동 빌드가 필요하다 — 개발 경험이 불편하다
- 실제 재현율 측정이 주관적 비교(스크린샷)에 그쳤다 — 체계적인 측정 기준이 없다
- 문서 작성이 작업 말미에 몰렸다 — 작업하면서 병행 기록하면 더 정확할 것
